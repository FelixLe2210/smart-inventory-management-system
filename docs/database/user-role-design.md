# User and Role Design

## Scope

The system uses a many-to-many relationship between `Users` and `Roles`:

```text
Users (1) -------- (*) UserRoles (*) -------- (1) Roles
```

This allows one user to hold more than one role while keeping role definitions
centralized. `UserRoles` uses `(UserId, RoleId)` as its composite primary key so
the same role cannot be assigned to the same user twice.

## Core tables

### Users

| Column | Responsibility |
| --- | --- |
| `UserId` | Surrogate primary key |
| `Username` | Login identifier; must be unique and normalized by the application |
| `PasswordHash` | One-way password hash; never store a password or reversible encryption |
| `FullName` | Display name and audit information |
| `Email` | Contact and notification address; should be unique when present |
| `IsActive` | Enables or disables login without deleting history |
| `CreatedAt` | Creation timestamp, set by the database |

### Roles

| Role | Purpose |
| --- | --- |
| `Admin` | Manages users, roles, system configuration, and has full operational visibility |
| `Warehouse Staff` | Performs day-to-day receiving, put-away, picking, packing, and stock movement tasks |
| `Warehouse Manager` | Supervises warehouse operations, approves adjustments, and reviews inventory reports |
| `Procurement Staff` | Creates and tracks purchase requests/orders and receives supplier-related information |

### UserRoles

`UserRoles` is the assignment table. Both foreign keys should be indexed and use
`ON DELETE CASCADE` only if deleting a user or role is an intentional operation.
In normal operation, prefer deactivating users and retaining role history.

## Role capability matrix

| Capability | Admin | Warehouse Staff | Warehouse Manager | Procurement Staff |
| --- | :---: | :---: | :---: | :---: |
| Sign in and view own profile | Yes | Yes | Yes | Yes |
| Manage users and role assignments | Yes | No | No | No |
| View inventory and stock levels | Yes | Yes | Yes | Yes (read-only) |
| Receive and put away stock | Yes | Yes | Yes | No |
| Pick, pack, and dispatch stock | Yes | Yes | Yes | No |
| Create stock adjustment | Yes | Yes (request) | Yes | No |
| Approve stock adjustment | Yes | No | Yes | No |
| Create purchase request/order | Yes | No | Yes | Yes |
| Approve purchase order | Yes | No | Yes | Per policy |
| Manage suppliers and purchasing data | Yes | No | Yes | Yes |
| View operational reports | Yes | Limited | Yes | Purchasing reports |
| Change system configuration | Yes | No | No | No |

The application should enforce these capabilities at the API/service boundary,
not only by hiding buttons in the frontend. A user with multiple roles receives
the union of the allowed capabilities, while approval actions should still be
subject to the organization's segregation-of-duties policy.

## Recommended constraints

- `Users.Username` is unique and case-insensitive according to the database collation.
- `Users.Email` is unique if the product requires one account per email address.
- `Roles.RoleName` is unique.
- `UserRoles` has foreign keys to both parent tables and a composite primary key.
- Password hashes are generated by the backend using a password hashing algorithm such as BCrypt or Argon2.
- Login checks `IsActive = 1`; deactivation must not delete the user or assignments.
- Role names are stable identifiers. Display text may be localized separately.

## Initial role assignments

The database should be seeded with the four roles from
`docs/database/seed-user-roles.sql`. User creation and assignment should happen
through an authenticated admin workflow. Do not commit real password hashes,
production emails, or production user assignments to the repository.
